# 页面加载性能复核

2026-10-20 · production build · Chromium headless

## 结论

首页的主要瓶颈不是图片或音频，而是启动顺序和词库传输：旧实现先下载、解析完整词库，再请求应用 UI chunk，形成串行网络瀑布；浏览器词库还包含未使用的编辑字段，并重复保存 3,863 个句子辅助词对象。

本次调整后：

- 应用 UI chunk 与词库并行请求，移除一次串行等待。
- 浏览器词库使用版本化紧凑格式，645 个唯一辅助词只保存一次，选项和辅助词使用数字索引。
- 编辑用的可读 `content/words.json` 不参与首页加载，只在家长页点击来源链接时按需请求。
- 音频仍完全按需加载；首页不会预取 MP3。

## 测量结果

测试条件：150 ms RTT、1.6 Mbps 下载、4× CPU slowdown；每组 3 次全新浏览器上下文，等待首页标题出现。

| 指标 | 调整前 | 调整后 | 变化 |
| --- | ---: | ---: | ---: |
| 首页可用平均时间 | 2,121 ms | 1,873 ms | -248 ms / -11.7% |
| 浏览器词库原始大小 | 768,387 B | 208,806 B | -72.8% |
| 浏览器词库 gzip | 89,364 B | 58,059 B | -35.0% |
| 浏览器词库 Brotli | 61,087 B | 44,750 B | -26.7% |

首屏加载提示的 FCP 基本不变（约 1.0 秒），因为它由 React runtime 和基础 CSS 决定；真正首页从约 2.12 秒提前到约 1.87 秒。调整后 UI chunk 和词库均约在 0.86 秒开始请求；旧实现 UI chunk 要等词库在约 1.49 秒结束后才开始。

## 保留的取舍

- 未添加 HTML fetch preload：现有 WebKit 验证显示可能重复下载同一词库。
- 未把学习页拆成延迟 chunk：这会改善纯首页数字，但会增加刷新正在学习页面和首次点击“开始学单词”的等待。
- 未添加 service worker：当前内容哈希已经避免版本混淆，而离线缓存会增加更新与故障恢复复杂度。

当前剩余关键路径约为 React runtime 71.1 KB gzip、应用 UI 18.2 KB、CSS 6.6 KB 和浏览器词库 58.1 KB。后续若需要更大幅度提升，应先用真实移动网络数据确认 React runtime 是否仍是主瓶颈，再评估 Preact 或服务端静态首屏；这两项都属于架构变更，不适合作为本轮低风险优化。
